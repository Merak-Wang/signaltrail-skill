# 证据驱动的专业叙事日报产品规格

**目的：** 定义证据驱动新闻讲解及后续媒体投影的计划中阅读体验、范围、质量承诺与发布标准。
**状态：** 草案
**负责人：** 仓库维护者
**最后验证：** 2026-08-28

本文记录的全部能力仍处于 **Draft / Planned** 状态。当前 SignalTrail 运行时交付既有报告契约
定义的权威日报。本提案从该报告完成并通过验证之后开始。组件设计见
[架构记录](../design-docs/evidence-driven-professional-narrative-report.md)，分阶段交付见
[活动执行计划](../exec-plans/active-evidence-driven-professional-narrative.md)。

## 产品结果

SignalTrail 计划把一个报告 revision 中的精选事件和既有研判组织成连贯的新闻讲解。读者完成
阅读或收听后，应清楚理解：

- 发生了什么，哪些信息仍不确定；
- 哪些证据支持每一项重要表述；
- 行为体、激励、约束与因果机制如何连接这些事件；
- 可信解释之间有哪些分歧；
- 哪些假设支撑当前判断；以及
- 哪些可观察信号可能加强、削弱或改变判断。

叙事始终绑定提供证据的报告与索引。它以适合阅读和收听的自然语言呈现材料，同时保留可见的
来源归因、时间语境、不确定性和验证状态。

## 目标用户

这项计划能力面向需要可解释简报、希望获得比标题列表更完整理解的读者。典型用途包括管理层
晨会材料、分析师交接、团队简报，以及对一版已完成日报的口播回顾。

同一产品契约适用于不同智能体 harness。各 harness 可以采用不同的 Provider 路由、委派、调度
和用量观测方式。这些差异不得改变叙事的证据要求或发布判定。

## 阅读体验

每版叙事先提供简短导读，再进入少量章节。每章围绕一个中心问题，把相关新闻、必要背景、研判
和观察信号连成一段连续解释。

展示层应让读者自然理解以下区别，无需显示内部字段清单：

- 已确认信息与经归因的表述；
- 历史或语境背景；
- 有依据的解释与因果推理；
- 反证、替代解释与不确定性；
- 条件情景及其假设；以及
- 可观察的后续信号。

读者可以展开章节或 claim 背后的证据。来源名称、发布时间、访问状态、报告 `as_of` 时间和验证
结果会保留在阅读视图中。正文可以运用节奏、铺垫和转场等叙事手法；所有事实细节和引语继续
遵循报告的证据边界。

## 计划范围

### 1. 证据驱动新闻讲解

第一阶段计划从一个已完成的报告 revision 及其匹配索引生成版本化叙事脚本，范围包括：

- 以精选事件、三个分析视角和可用的跨视角综合为基础组织章节；
- 形成可独立追溯和审阅的精简 claim 或 beat 单元；
- 清楚表达证据质量、时效、分歧与不确定性；
- 在任何叙事获得“已验证”状态前完成确定性校验；
- 从同一个已接受语义 revision 生成本地 HTML 与 Markdown 阅读视图；以及
- 在活动 harness 能够提供时保存用量和耗时观测。

**Claim** 是重要的事实性或分析性表述。**Beat** 是包含一个或少量紧密相关 claim 的小型读者
可见单元。实现阶段可以根据原型调整其精确 Schema；可追溯和可验证的用户承诺保持稳定。

### 2. 独立 claim 与 beat 验证

独立 verifier 使用父报告授权的证据审阅叙事。验证覆盖证据支持、归因、时间语境、认知措辞，
以及重要遗漏或矛盾。Verifier 输出与脚本、报告和索引 Hash 绑定的结构化判定。

失败或不完整的验证会让叙事保持可审阅的 Draft 状态。后续 revision 可以处理问题并获得新的
验证结果。进入阅读发布和媒体阶段前，必须具备当前有效的验证回执。

### 3. Story stream 与授权素材

后续计划阶段把已验证 beat 转换为 story stream，即用于视觉讲解的有序场景计划。每个场景链接
其服务的已验证 beat，并记录所选素材的来源与使用权利。

素材可以来自经批准的公开来源、仓库自有媒体、获得许可的素材库，或具有来源记录的专门生成
视觉。找不到合适授权素材时，系统使用确定性备用方案。

### 4. 音频、字幕与新闻讲解视频

后续媒体阶段计划加入：

- 具有语音与引擎来源记录的授权 TTS；
- 根据实际口播时长对齐的字幕；
- 由已验证脚本和 story stream 构建的可复现新闻讲解视频；以及
- 媒体交付前的技术与权利审查。

各媒体阶段可以独立发布。媒体失败时，已验证文字叙事仍然可用。

## 产品边界

首个计划版本排除以下能力：

- 直播或自动发布到公共频道；
- 冒充、未经许可的声音克隆和合成引语；
- 权利未知或许可不兼容的素材；
- 无法确认权利与来源的视频素材摄取；
- 虚构场景、对话、动机、时间顺序或内幕信息；
- 个性化金融、法律、医疗或军事行动建议；以及
- 修改权威报告、索引或其连续性历史。

该能力解释 SignalTrail 已经准入的证据。来源采集、访问验证、报告写作和既有报告质量门继续
保有各自权威。

## 版本与证据契约

每一份已接受叙事都具有 Schema 版本、自身不可变 revision，以及父报告和索引 Hash。验证与
媒体工件标识其使用的精确叙事 revision。父内容发生变化时，下游进入新的依赖状态，并需要
新的验证判定。

产品契约为实现阶段保留学习空间。精确文件名、函数签名、Prompt 格式、模型选择和场景渲染器
API 会在交付过程中确定；只有形成持久边界后才进入架构记录。

## 质量原则

- **可追溯：** 重要 claim 能够指向父报告中的授权证据。
- **清晰：** 读者能够区分观察、归因、解释和不确定性。
- **解释价值：** 叙事连接原因、约束、激励与后果。
- **辩证深度：** 重要反证和替代解释得到公平处理。
- **时效：** 当前判断公开其时间基础；基础变化后，判断过期或返回审阅状态。
- **Revision 完整性：** 已接受工件可从记录的父项复现，且不会被静默覆盖。
- **Harness 一致性：** 无论使用哪个 harness 编排模型工作，同一版内容都采用相同验收标准。
- **权利安全：** 每一项交付媒体素材都具有允许使用的来源与权利状态。

## 精简验收模型

既有 G0–G7 名称继续作为发布标签。每个门禁只保留一个主要判定和少量可观察结果。

| 门禁 | 计划判定 | 最低可观察结果 |
| --- | --- | --- |
| G0 — 父项绑定 | 叙事是否基于一个已完成且当前有效的报告 revision？ | 报告与索引身份、revision 和 Hash 与声明的父项一致。 |
| G1 — 证据和时效 | 重要 claim 是否在声明的时间与认知角色下得到支持？ | 每个关键 claim 都有授权证据或明确的未解决结果；过期证据不能获得当前有效的验证判定。 |
| G2 — 叙事质量 | 本版内容是否连贯解释事件并处理可信分歧？ | 编辑审阅按版本化发布阈值通过清晰度、解释力、反方处理、不确定性和实用性。 |
| G3 — 独立验证 | 隔离 verifier 是否审阅了完整 claim 与 beat 集合？ | 每个已发布 beat 都有最终结构化判定，验证回执覆盖精确脚本 revision。 |
| G4 — 成本和观测 | 模型工作是否可以归因并处于获批运行预算内？ | 必要阶段具有精确或显式不完整的用量覆盖；发布候选处于版本化预算内。 |
| G5 — Revision 与恢复 | 重放、中断和并发工作能否保存历史？ | 既有 revision 保持不变；身份相同的工作避免重复；可恢复失败保留明确状态。 |
| G6 — 阅读投影 | 各阅读格式是否承载同一份已验证语义？ | HTML 与 Markdown 标识同一语义 revision，并保留证据链接和安全渲染。 |
| G7 — 媒体准入 | 每个媒体阶段是否使用当前已验证内容和授权素材？ | Draft、过期、不匹配或权利未知的输入不能进入已发布 story stream、音频、字幕和视频。 |

汇总质量分可以辅助编辑审阅。父项、证据、验证、revision 或权利判定失败时，汇总分不能改变
门禁结果。

## 真实日报验收

自动化 fixture 先建立确定性行为。产品发布随后需要跨至少两个智能体 harness 连续完成三期真实
日报，其中至少包含一份晨报和一份晚报。

三期中的每一期都满足：

- 该发布候选所包含阶段的 G0–G7 全部通过；
- 读者可以把一组有代表性的关键 claim 追溯到父报告证据；
- 独立 verifier 与编辑审阅都确认不存在未解决的关键问题；
- 本版处于记录的耗时与模型用量预算内，超限时形成被阻断结果；
- 重放与投影检查保留相同 revision 和 Hash；以及
- harness 专属编排细节不会进入读者内容或改变验收结果。

Story stream、音频、字幕与视频在各自阶段实现后分别进行真实验收。其发布证据还包括权利审查
和技术播放检查。

## 发布状态

证据驱动新闻讲解、独立 claim 与 beat 验证、story stream、授权素材选择、TTS、字幕、新闻
讲解视频，以及跨多 harness 连续三期验收，全部仍处于 **Draft / Planned** 状态。

只有当实现、Schema、自动化测试、真实日报证据、用户文档与英中文记录描述同一套已交付行为时，
本文才可以转为“已验证”。
