# 证据驱动专业叙事交付计划

**目的：** 跟踪权威 SignalTrail 报告下游的已验证专业叙事、story stream 与可选媒体投影的
分阶段实现和验收。
**状态：** 进行中
**负责人：** 仓库维护者
**最后验证：** 2026-08-28

本文是[架构记录](../design-docs/evidence-driven-professional-narrative-report.md)与
[产品规格](../product-specs/evidence-driven-professional-narrative-report.md)所定义能力的持久执行记录。
已经完成的计量与 Token 优化基础另见
[2026-08-23 实现记录](completed-2026-08-23-llm-usage-optimization-implementation.md)。

## 目标

交付自然、专业的故事化表达层，在不削弱证据边界的前提下解释精选新闻与辩证研判。不可变
报告和索引继续作为事实权威；叙事、story stream、音轨或视频只是下游投影，不能修改或撤销
一份有效报告。

只有经过独立验证、仍然当前且与上游哈希绑定的脚本才能进入阅读器或媒体阶段。被拒绝、过期、
不完整或哈希不匹配的脚本继续作为可见证据保留，但绝不晋级。

## 交付顺序

```text
不可变报告 + 不可变索引
-> 有界叙事 packet
-> 故事讲述者草稿
-> 确定性校验
-> 不可变规范脚本 revision
-> 独立逐 beat 验证
-> 不可变已验证闸门回执
-> 阅读投影
-> 确定性 story stream
-> 合法授权的 TTS + 字幕
-> 可复现视频 + 媒体与权利 QA
```

## 工作包

1. 为 packet、脚本、验证和闸门回执定义严格 Schema、类型化状态、不可变仓库、哈希与恢复规则。
2. 从完全完成的报告构建有界 packet，接收一次故事讲述者提交，并且所有阶段共用至多一次修复。
3. 独立验证每个 beat，只通过一个公共加载器返回仍然当前的类型化已验证能力。
4. 在不改变权威报告内容或连续性状态的前提下，把已验证叙事渲染到本地 HTML 和 Markdown。
5. 使用已验证 beat 和显式备用媒体，编译确定性、考虑权利状态的 story stream。
6. 仅在 story-stream 闸门通过后加入合法授权的 TTS、实测字幕、可复现视频渲染及技术/权利 QA。

## 验收闸门

- Python 拥有 ID、revision、哈希、证据授权、新鲜度、状态、修复上限、持久化和下游准入。
- 最终已验证 claim 至少覆盖 60% 的不同精选事件、全部三个研判领域，以及版本化契约要求的
  跨视角综合。
- 独立验证器通过每个最终 beat；失败不能被部分媒体输出或强制开关掩盖。
- 连续三版完全验收的报告（至少一份晨报和一份晚报）通过预冻结的 Version 1 Token 上限及全部
  质量/证据闸门。
- 任一阶段晋级前，完整仓库门禁必须同时在 Windows 与 Linux 通过。

## 恢复与回滚

- 每次尝试、脚本 revision、验证和闸门回执均不可变并采用防碰撞写入。
- 报告、索引、契约、packet、脚本或新鲜度判断发生变化时，下游工作失效，而不是静默迁移。
- 关闭或失败的叙事/媒体阶段不会影响权威报告的已交付和有效状态。
- 阅读器与媒体入口只接受显式已验证 bundle；不扫描“最新”文件，也不接受原始对象、部分 beat
  集合或绕过开关。
